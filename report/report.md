### 4.1 基础原理、管理框架与启动分页

本节按“地址与页表原理—软件管理结构—启动落地”的顺序组织，分别标注负责人。

#### 4.1.1 页、物理地址空间与 Sv39

**负责人：2410936 林子媛**

##### 页、地址空间与碎片

页是按固定大小切分地址空间得到的单位，不是某一个 C 结构体。以 4 KiB 基本页为例，一页含 4096 字节，同页内各字节共享页级映射，转换时保留低 12 位偏移。虚拟页属于虚拟空间，物理页帧是 RAM 中的一段，`struct Page` 只是描述物理页帧的元数据。

如果逐字节记录映射，管理开销很大；按页翻译后，一条映射可以描述整页。不同进程可把相同虚拟地址映射到不同物理页，避免地址冲突；也可以有意映射同一物理页实现共享。连续虚拟页可对应不连续物理页，从而降低程序对物理连续空间的依赖。

分页没有消除全部碎片：固定页与 size class 会产生内部碎片；本实验的大对象仍申请连续物理页，即使总空闲页数足够，也可能因外部碎片找不到足够大的连续块。换页则还需要缺页异常、后备存储和置换算法，本实验只理解其基础，没有实现完整换页。

##### 物理地址空间不等于可用 RAM

手册给出的 QEMU `virt` 布局包括 RAM、ROM、MMIO 和未映射空洞。以下采用左闭右开区间列出主要区域：

| 物理区间                       | 手册中的含义              | 是否交给普通页分配器 |
| -------------------------- | ------------------- | ---------- |
| `[0x0, 0x100)`             | VIRT_DEBUG          | 否          |
| `[0x1000, 0x12000)`        | MROM、复位相关内容         | 否          |
| `[0x100000, 0x101000)`     | VIRT_TEST           | 否          |
| `[0x02000000, 0x02010000)` | CLINT，中断/定时器相关 MMIO | 否          |
| `[0x0c000000, 0x10000000)` | PLIC 中断控制器          | 否          |
| `[0x10000000, 0x10000100)` | UART0               | 否          |
| `[0x10001000, 0x10002000)` | VirtIO MMIO 示例窗口    | 否          |
| `[0x20000000, 0x24000000)` | Flash               | 否          |
| `[0x30000000, 0x40000000)` | PCIe ECAM           | 否          |
| `[0x40000000, 0x80000000)` | PCIe MMIO           | 否          |
| `[0x80000000, 0x88000000)` | 默认 128 MiB DRAM     | 排除保留区后管理   |

未列出的区间不能自动视为普通空闲内存。设备布局可能随 QEMU 版本调整，实际探测应结合设备树，不能只因地址落在一个大范围内就当作 RAM。

本次启动输出的 DRAM 基址是 `0x80000000`，大小为 `0x08000000`。`-m` 可以改变模拟机提供的 RAM，但当前 `memlayout.h` 把可管理上界限制在 `0x88000000`；`page_init()` 会限制管理范围，增大 QEMU 内存并不代表会自动管理全部新增空间。低于内核物理起点 `0x80200000` 的实验保留区、内核镜像和描述符数组都不能进入空闲链表。

##### Sv39 地址、PTE 与权限

Sv39 使用 39 位有效虚拟地址，但 RV64 寄存器和指针仍为 64 位。位 `[63:39]` 必须全部等于位 38；任意 64 位数不一定是合法地址。有效地址组合共 `2^39 = 512 GiB`，在 64 位表示中分为低端和高端两个规范地址区，不是一段连续的低 512 GiB 区间。

```text
VA: [63:39] 符号扩展 | [38:30] VPN[2] | [29:21] VPN[1] | [20:12] VPN[0] | [11:0] offset
位数:      25               9                9                9              12
```

每张页表为 4 KiB，每项 PTE 为 8 字节，共 512 项，恰好用 9 位索引。普通 4 KiB 映射最多用三级查表。Sv39 的物理页号字段最多为 44 位，配合 12 位偏移最多表示 56 位物理地址；这不是本次模拟机拥有如此大 RAM 的意思。

| PTE 位     | 字段        | 含义                    |
| --------- | --------- | --------------------- |
| 0         | V         | 有效标志，无效项不能作为正常映射使用    |
| 1 / 2 / 3 | R / W / X | 读、写、执行权限，也参与区分叶项与非叶项  |
| 4         | U         | 用户态访问标记，本次启动叶项为 0     |
| 5         | G         | 全局映射标记，不等于“内核页”；本次未设置 |
| 6 / 7     | A / D     | 访问状态、写入/脏状态           |
| `[9:8]`   | RSW       | 留给监督态软件使用，不作为物理页号     |
| `[53:10]` | PPN       | 非叶项指向下级页表；叶项给出映射物理页号  |
| `[63:54]` | 保留或扩展用途   | 本实验不使用相应扩展，保持为零       |

需要注意以下权限边界：

1. `V=1` 且 `R/W/X=000` 的项表示继续查下一级；合法叶项具有 R 或 X。`W=1、R=0` 是保留组合，不能作为正常只写页。
2. 常用叶权限包括只读、读写、只执行、读执行、读写执行；`MXR` 可影响只执行页能否被按数据读取，但不允许绕过任意权限。
3. `SUM` 位位于状态寄存器，不在 PTE 中，控制 S-mode 对 U 页的数据访问。S-mode 不能仅靠设置 SUM 就执行 U 页代码。访问还要结合特权级与 PMP 等检查。
4. A/D 的维护取决于相应架构机制和实现。本次启动 PTE 已将二者置 1，不把成功启动当作已验证完整的 A/D 缺失处理。

字段含义参考 [RISC-V Supervisor-Level ISA](https://docs.riscv.org/reference/isa/v20260120/priv/supervisor.html)，本实验使用的具体项以 `entry.S` 和实际读取结果为准。

多级页表按需建立下级表，不必为整个未使用空间准备平坦大表，但根表和必要的中间表本身也占内存。各级可以提前成为叶项：末级为 4 KiB，中间级为 2 MiB，根级为 1 GiB。大页要求相应物理基址对齐，形成地址时保留的大页内偏移更长。

##### 本项目的启动映射与 satp

RV64 `satp` 包含 MODE `[63:60]`、ASID `[59:44]`、PPN `[43:0]`。MODE=0 为 Bare，8 为 Sv39，9 为 Sv48；Sv48 增加一级索引，本实验没有启用。ASID 区分地址空间，具体支持位数由实现决定；本次 ASID 为 0。

本项目保留的高地址根项为：

```text
root[511] = (0x80000 << 10) | 0xcf = 0x200000cf
0xcf      = V | R | W | X | A | D
```

该项直接把从 `0xffffffffc0000000` 开始的高地址 1 GiB 窗口映射到从 `0x80000000` 开始的物理窗口。内核链接起点为 `0xffffffffc0200000`，物理加载起点为 `0x80200000`；在有效直接映射内相差 `0xffffffff40000000`。映射窗口大于本次真实 RAM，PTE 存在不代表窗口内所有物理位置都存在内存。

开启分页不会自动改写 PC。当前汇编临时设置根项 2 的低地址恒等映射，保证写 `satp` 后还能取指；进入高地址后清除此项，再执行 `sfence.vma`。后者用于地址翻译同步，不是普通数据缓存的通用刷新命令，写 `satp` 也不能替代其全部作用。

SLUB 因此不需要为每个对象修改页表：启动直接映射已经使管理范围内的 RAM 可通过内核虚拟地址访问，SLUB 只是改变页面归属和页内对象布局。

#### 4.1.2 Page、链表与 pmm_manager

**负责人：2410933 马禹翔**

##### `Page` 描述符与物理页

物理页是物理内存中按 `PGSIZE` 划分的一段真实空间；`struct Page` 是内核为物理页保存的软件元数据。二者不能混为一谈。项目用连续的 `pages[]` 数组描述从 `nbase` 开始的物理页，转换关系为：

```c
page2ppn(page) = page - pages + nbase;
page2pa(page)  = page2ppn(page) << PGSHIFT;
```

`struct Page` 的四个字段含义如下：

- `ref`：页框引用计数。本实验的连续页分配测试主要把它初始化为 0；它不等价于“该页一定空闲”。
- `flags`：状态位集合。`PG_reserved` 表示页面尚不能交给普通分配器，`PG_property` 表示该描述符是空闲连续块的块头。
- `property`：块级元数据。First Fit/Best Fit 中只在带 `PG_property` 的空闲块头上表示连续页数；Buddy 中空闲块头保存实际的 2 的幂块大小，已分配块头也暂存向上取整后的实际大小以校验释放参数。
- `page_link`：嵌入在 `Page` 中的双向链表节点。空闲链表只挂块头，不会把同一连续块中的每个页都挂入链表。

因此，仅看到 `property != 0` 不能断言某页是空闲块头，必须同时检查 `PageProperty(page)`。同样，`flags` 只是描述符的一个字段，并不是完整的物理页描述符。

##### 空闲链表与成员指针转换

`list_entry_t` 是带 `prev/next` 的循环双向链表节点。链表头是哨兵，不对应实际 `Page`；空链表满足 `head.next == head`。`list_add()` 在指定节点之后插入，`list_add_before()` 在指定节点之前插入，`list_del_init()` 删除节点后将其重新初始化为自环。

链表节点嵌在 `struct Page` 中，遍历得到的是 `page_link` 的地址。项目通过以下宏恢复外层对象：

```c
#define offsetof(type, member) ((size_t)(&((type *)0)->member))
#define to_struct(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))
#define le2page(le, member) to_struct((le), struct Page, member)
```

其思想是“成员地址减去成员在结构体中的偏移量，得到结构体首地址”。`free_area_t` 中的 `free_list` 保存块头节点，`nr_free` 保存空闲页总数，不是链表节点数；一个 16 页块在链表里只有一个节点，但会给 `nr_free` 贡献 16。

##### `pmm_manager` 统一接口

`struct pmm_manager` 用函数指针隔离通用框架与分配策略：

| 字段              | 责任                                  |
| --------------- | ----------------------------------- |
| `name`          | 管理器名称，用于启动输出和核对当前实现                 |
| `init`          | 初始化算法自己的链表、分组和计数，不登记真实页             |
| `init_memmap`   | 接收上层确认可用的 `[base, base+n)`，建立初始空闲结构 |
| `alloc_pages`   | 分配连续页并返回块头，失败返回 `NULL`；实际长度遵守所选算法约定 |
| `free_pages`    | 释放从 `base` 开始的页面并按算法规则合并            |
| `nr_free_pages` | 返回空闲页总数，不改变状态                       |
| `check`         | 运行该管理器自己的正确性断言                      |

`pmm.c` 中的 `alloc_pages()`、`free_pages()`、`nr_free_pages()` 只是统一包装，真正操作由当前 `pmm_manager` 完成；`alloc_page()` 和 `free_page()` 是单页宏。实际初始化顺序为：

```text
kern_init
  -> pmm_init
       -> init_pmm_manager       选择算法并调用 manager->init()
       -> page_init              发现内存、建立 Page 数组和保留区
            -> init_memmap       调用 manager->init_memmap(base,n)
       -> check_alloc_page       调用 manager->check()
```

不是“`pmm_manager` 先主动启动，再调用 `pmm_init()`”。`page_init()` 也不是另一个并列入口，而是 `pmm_init()` 内部把真实空闲区交给所选算法的阶段。

#### 4.1.3 启动映射设计、六问及分页切换

**负责人：2410673 韩羽宸**

**高地址链接与物理加载。** 链接脚本将 `BASE_ADDRESS` 设为 `0xffffffffc0200000`，ELF 中内核符号按这个高地址布局；QEMU 将裸内核镜像加载到物理地址 `0x80200000`。两者之差是 `0xffffffff40000000`。链接脚本决定地址安排，真正的运行时翻译仍由页表和 `satp` 配合完成，修改链接地址不会自动启用分页。

进入 `kern_entry` 时，实际观测到 PC 为 `0x80200000`、`satp = 0`，处于 Bare 地址转换模式，S 模式取指按物理地址进行。本轮继承的 SP 为 `0x8003def0`，属于固件启动现场；它不是内核自己的栈，也不是以后每次运行都固定不变的接口。内核在进入 C 之前换成自身分配的栈。

符号的链接地址与指令执行算出的地址要分别分析。`la`、`tail` 是伪指令，其结果与展开方式有关，不能概括为“高地址链接以后每条 `la` 都会生成高地址”。当前保存启动参数的 `la` 展开为 PC 相对的 `auipc/addi`，在低地址启动时能算出镜像中变量的物理位置。旧实验只用 `la sp`、`tail kern_init` 并不能保证建立高地址虚拟空间，即使某些 PC 相对跳转暂时仍能在低地址继续执行，也不等于高地址映射已经存在。

**分页设计六问。** 以下逐项对应手册“建立段页式管理中需要考虑的关键问题”。

1. **哪些物理空间需要映射？** 启动执行需要访问内核代码、数据、BSS、启动栈、根表、DTB，以及随后用于页描述符和分配的 RAM。本项目用一个根级大页简化覆盖从 `0x80000000` 起的 1 GiB 物理窗口，即 `[0x80000000, 0xc0000000)`。这是地址映射窗口；本轮真实 RAM 只有 `[0x80000000, 0x88000000)`，不能因为有 PTE 就把窗口剩余部分当成存在的 RAM。OpenSBI 所在的实验保留区虽落在窗口内，也不能交给分配器，实际访问还受 PMP 等权限约束。

2. **具体映射关系是什么？** 高地址区从 `0xffffffffc0000000` 开始，直至 64 位地址的最大值，对应上述物理窗口。用闭区间写即高地址 `[0xffffffffc0000000, 0xffffffffffffffff]` 映射到物理 `[0x80000000, 0xbfffffff]`。对这个窗口中的有效访问，`PA = VA - 0xffffffff40000000`。内核入口位于窗口内偏移 2 MiB 处，因此 `0xffffffffc0200000` 对应 `0x80200000`。当前修复还在过渡期用根表第 2 项临时提供低地址恒等映射，进入高地址后移除。

3. **页目录表起始地址在哪里？** Sv39 的根表符号为 `boot_page_table_sv39`。本次观测虚拟地址是 `0xffffffffc0205000`，物理地址为 `0x80205000`，物理页号为 `0x80205`。硬件通过 `satp.PPN` 定位它，不能把符号的高虚拟地址直接写成根表物理页号。

4. **页表放在哪里、需要多少空间？** 根表在 `entry.S` 的 `.data` 段静态分配并按 4 KiB 对齐，共 512 个 8 字节项，总大小 4096 字节。当前根项直接作为 1 GiB 叶项，没有继续为该映射分配中间和末级表。一般 Sv39 支持三级结构，但本实验当前用到的表内存只有一个根表页，不能说必然用了三张表。

5. **怎样设置页目录项？** Sv39 各级使用同一种 PTE 格式。若有效项的 R/W/X 均为零，它才作为通向下一级表的非叶项；有合法的 R 或 X 权限组合时可作为叶项。当前根表第 511 项是叶项，第 2 项仅在启动过渡期有效，其余项为零。进入 C 后实测只剩第 511 项有效，前 511 项为零。根表中使用了叶项，所以此处不存在另一个必须指向的下级目录。

6. **怎样设置页表项内容？** 目标 1 GiB 物理窗口的基址为 `0x80000000`，先取物理页号 `0x80000`，再移到 PTE 的 PPN 字段，得到 `(0x80000 << 10) | 0xcf = 0x200000cf`。低位 `0xcf` 表示 V、R、W、X、A、D 为 1，U、G 为 0；它是内核可读写执行、预置访问和脏标记的叶项，不是用户映射，也没有设置全局位。1 GiB 叶项的虚实基址均满足 1 GiB 对齐，不能把没有这样对齐的任意内核页地址直接填作根级大页基址。

六问中的“目录表”和“页表”是按层级职责提出的问题，Sv39 并不使用两种不同格式的表项。本项目根表同时承担叶表的功能。Sv39 允许不同级别的叶项以及对应的大页对齐要求，和规范一致。[RISC-V Supervisor ISA](https://docs.riscv.org/reference/isa/priv/supervisor.html)

**`satp` 与翻译同步。** RV64 的 `satp` 包含 MODE、ASID 和根表物理页号。当前使用 MODE=8（Sv39）、ASID=0、PPN=`0x80205`，所以数值为 `0x8000000000080205`。右移 12 位的是根表物理地址，不是整个 `satp`。Sv39 虚拟地址按规范进行高位符号扩展校验，不能把任意 64 位值都当成有效 Sv39 地址。

`sfence.vma` 用于页表更新与随后地址翻译之间的同步，并使相关翻译缓存状态满足新映射的要求。写 `satp` 本身不等于完成页表更新排序或翻译缓存失效；这里使用不限定地址、ASID 的形式。它不是刷新所有普通数据缓存或指令缓存的通用命令。[RISC-V 对 satp 与 SFENCE.VMA 的说明](https://docs.riscv.org/reference/isa/priv/supervisor.html)

**从低地址到高地址的真实过程。** 开启分页不会替 CPU 自动改写 PC。本次在 `csrw satp,t0` 执行后，PC 仍为低地址 `0x80200038`，而 `satp` 已变为 Sv39；临时根项确保下一条指令仍能取到。随后跳至 `0xffffffffc0200046`，在高地址清除根表第 2 项并执行 `sfence.vma`，再设置高地址栈并跳到 `kern_init()`。如果只保留高地址项却不处理这段过渡，低地址下一次取指就可能产生页错误；实际集成时已经用真实 `scause/stval` 定位并修复了这一问题。

**一般三级页表与本次大页。** Sv39 的地址索引可分成 VPN[2]、VPN[1]、VPN[0] 和 12 位基本页偏移；根表、中间表、末级表分别可以形成 1 GiB、2 MiB、4 KiB 的叶映射。本次根项已是叶项，因此转换在根级结束，1 GiB 内的低 30 位作为大页内偏移。例如实际 C 入口 `VA=0xffffffffc02000ee`，根索引为 511，窗口内偏移为 `0x2000ee`，所以 `PA=0x80000000+0x2000ee=0x802000ee`。这是基于已读取 PTE 的地址计算，尚不等于已经在 QEMU 源码中单步看到页表遍历，实际 QEMU 源码单步另见 4.8。

### 4.2 功能模块一：物理内存探测与页初始化

**负责人：2410673 韩羽宸**

**任务、接口和职责。** 实际实现入口为 `static void page_init(void)`，由 `pmm_init()` 调用，不接收参数、不返回值。它消费 DTB 查询结果并建立初始页状态，不重新解析 DTB，也不负责 Best Fit 的搜索。关联接口为 `void dtb_init(void)`、`uint64_t get_memory_base(void)`、`uint64_t get_memory_size(void)`，以及内部委托 `static void init_memmap(struct Page *base, size_t n)`。实现见 [pmm.c](../code/kern/mm/pmm.c)。

**启动参数与 DTB 解析。** OpenSBI 以 a0 传入 hartid，以 a1 传入 DTB 物理地址，本轮为 0 和 `0x87000000`。`entry.S` 在改用这些寄存器之前保存到 `.data` 中的 `boot_hartid`、`boot_dtb`，因此 C 中清零 BSS 不会清掉参数。`dtb_init()` 使用编译期 `PHYSICAL_MEMORY_OFFSET` 将 DTB 地址转换为 `0xffffffffc7000000`，不依赖尚未由 `page_init()` 设置的全局偏移。

解析器验证非零地址和魔数 `0xd00dfeed`，按大端格式转换头部、结构标记和属性中的数值；头部偏移确定结构块、字符串块位置。`FDT_BEGIN_NODE` 识别节点，`FDT_PROP` 通过名称偏移查找属性，在 memory 节点中读取 `reg` 的起点和长度，处理必要的 4 字节对齐；`FDT_END_NODE`、`FDT_NOP` 和 `FDT_END` 控制遍历。结果保存到静态 `memory_base/memory_size`，由 getter 交给 PMM。当前 `dtb.c` 是框架提供的简化解析器，并非本人从零实现的通用设备树库。

空 DTB、错误魔数或未找到内存时，解析器打印信息并返回，当前启动的查询结果仍为零；后续 `page_init()` 校验并终止。不能把这些路径写成解析器本身全部 panic。当前代码没有完整遍历多段 RAM、保留区和通用 cell 编码，也不对任意损坏 DTB 提供完整边界防护。本实验遵循手册的可信启动 DTB 与单段 RAM 条件。

**四种地址和页数。** `end`、`pages` 是内核虚拟地址；RAM 起点、`maxpa`、`freemem` 是物理地址；`nbase/npage` 是物理页号；`struct Page *` 指向管理记录，不是待分配物理页的地址。

```text
nbase = DRAM_BASE / PGSIZE = 0x80000
npage = 管理末端物理地址 / PGSIZE = 0x88000（本次128 MiB）
描述符数量 = npage - nbase = 32768
page2pa(pages+i) = (nbase+i) << 12
pa2page(pa) = pages + (PPN(pa)-nbase)
```

`npage` 虽在旧注释中容易被理解为“页面数量”，实际是页号上界。把它直接当数组元素数会多算从零到 DRAM_BASE 的巨大空洞。`pa2page()` 的当前实现只显式检查上界，调用方仍须保证地址不低于 DRAM_BASE，不能将它当成任意地址的完整验证器。

`PADDR(kva)` 从内核虚拟地址减去全局偏移，当前宏检查其不低于 KERNBASE；它不执行硬件查表。手册给出 `KADDR` 反向转换思路，但本工程中的宏处于注释内，当前实现未调用它。因而报告说明转换关系，不把被注释宏写成正在使用的接口。

**布局和初始化步骤。** 实现先校验起点等于当前固定 DRAM_BASE、长度非零、起点加长度不溢出，再设置偏移。管理末端由真实内存末端与框架上界取较小值并向下按页对齐，必须能覆盖内核。描述符数组在虚拟 `end` 后向上对齐，写数组之前先检查整个数组容得下。

```text
maxpa = ROUNDDOWN(min(mem_base+mem_size, PHYSICAL_MEMORY_END), PGSIZE)
pages = ROUNDUP(end, PGSIZE)                 （虚拟地址）
page_count = npage - nbase
pages_pa = PADDR(pages)                     （物理地址）
freemem = ROUNDUP(pages_pa + page_count*sizeof(struct Page), PGSIZE)
可分配区 = [freemem, maxpa)
```

容量检查使用 `page_count > (maxpa-pages_pa)/sizeof(struct Page)`，先确定减法合法，再避免直接用一个过大乘积判断。全数组先置为引用计数零、`property=0`、保留标志置位、链表节点自环。只有确定可用的完整页面才交给当前管理器解除保留并登记，其他页面继续保留。

```text
低地址 → 高地址：
OpenSBI保留区 → 内核镜像（含启动栈/根表/BSS）→ 对齐空隙
             → Page数组 → 对齐空隙 → 可分配完整页 → 不完整尾部
```

本次完整测试镜像 `end=0xffffffffc0206078`，所以数组起点为 VA `0xffffffffc0207000`、PA `0x80207000`。当前 RV64 `sizeof(Page)=40`，32768 个元素共 `0x140000` 字节，即 320 页；空闲起点为 `0x80347000`。总共保留 839 页，剩余 31929 页。代码使用 `sizeof` 和链接符号计算，未写死这组数值；独立测试内核稍大时起点会不同。

**行为规格与边界。** 输入依赖 DTB 已解析、管理器已初始化且调用前没有登记可分配页。成功返回必须得到可管理范围、完整描述符和安全空闲区；零空闲页可以保留确定状态，但不能调用 `init_memmap()`。无效起点、零长度、溢出、内核或描述符容纳不下时，须在放出空闲页前终止。完整的前后条件、分支规格及最终提示词见 [HYC-P1](prompt.md#hyc-p1)。

**实现迭代与结果。** 按以上规格完成实际函数并保留 `//lab2 function1 2410673`。初始化算法第一次完整执行 13 个用例均通过，没有为报告编造反复修正算法的经历。测试搭建时确有 `sbi_shutdown()` 只有声明、没有定义导致的链接错误，仅在独立驱动中用局部 SBI 退出调用处理；正式 SBI 模块不变。初始化的完整运行证据见 5.1，边界验证见 5.2。

### 4.3 Challenge：可用物理内存范围的获取

**负责人：2410673 韩羽宸**

**题目：如果 OS 无法提前知道当前硬件的可用物理内存范围，有什么办法获取？**

可以让启动固件或引导程序按照约定，把运行时内存布局传给 OS。OS 不必把每台机器的 RAM 容量编译进内核，但必须知道怎样定位和解析这些启动信息。得到的应当是带起点、长度和用途的区间集合，而不能只有“装了多少 GB”一个总容量数。

在本实验中，入口寄存器 `a1` 提供 DTB 地址，内核读取 memory 节点的 `reg`，得到 RAM 起点与长度。完整设备树可以描述多段内存，且地址和长度的编码由相应 cell 数决定；保留区需要单独识别和排除。当前解析器只取找到的第一个地址、长度对，并没有实现通用多段解析及保留区处理。[设备树 memory 与 reserved-memory 约定](https://devicetree-specification.readthedocs.io/en/latest/chapter3-devicenodes.html)

其他平台可以采用不同的信息交付方式。例如传统 x86 BIOS 启动可由引导程序查询 E820 系统地址图，再将结果交给内核；UEFI 启动可在退出 Boot Services 前获取 `GetMemoryMap()` 返回的带类型内存描述符。后者需要依据类型区分可用 RAM、固件保留区和其他用途，不是拿到所有描述符就全部释放。本项目没有执行或实现这些固件接口，它们是 Challenge 的可行方法说明。[ACPI 系统地址图接口](https://uefi.org/specs/ACPI/6.5/15_System_Address_Map_Interfaces.html)、[UEFI GetMemoryMap](https://uefi.org/htmlspecs/ACPI_Spec_6_4_html/15_System_Address_Map_Interfaces/uefi-getmemorymap-boot-services-function.html)

若平台没有通用接口，也可由知道板级布局的固件依据内存控制器配置整理地址图，再按双方约定传递。此方法依赖平台文档，读取内存条容量信息本身不能自动给出所有实际映射、地址空洞和保留区。这是平台相关的补充思路，不是本次已经验证的探测程序。

获取原始区间后，还需检查起点加长度是否溢出、区间是否重复或冲突，区分 RAM 与 MMIO，并减去固件、内核、启动数据和管理元数据占用。最后将区间起点向上、末端向下按页对齐，只将确定可用的完整页交给分配器。对多段 RAM 应分别组织可用区，而不能假设从最低起点到最高末端之间全部存在内存。

不宜将“不断向更高地址写入测试值并读回”作为通用探测方案。未知物理地址可能属于 MMIO、保留数据或地址别名，写入会产生副作用；读写失败也可能来自访问权限而非 RAM 不存在。这一限制来自未知地址用途的风险分析。若完全没有平台信息或启动协议，就不能保证通过一段通用试探代码安全识别全部可用内存。

本实验按手册简化：DTB 中起点和长度提取后，后续不再需要 DTB 原结构，可以复用它占用的空间。真实系统若还要读取设备、CPU 或保留信息，应保留 DTB，或者完整复制后再释放，不能只因读过内存节点就复用。当前 `libs/sbi.h` 虽声明 `sbi_query_memory()`，实际 `sbi.c` 没有该实现，代码也没有走这条路径；不能据此宣称已经通过 SBI 自动查询全部物理内存。

因此，本题的完整回答是：**通过平台规定的启动信息获得内存区间和用途，再结合运行中必须保留的区域与对齐规则，形成可分配物理页集合。** 本次实现的是其中 DTB 单段内存的教学版本。

**最终提示词：** [HYC-P5](prompt.md#hyc-p5)。SPEC 要求回答信息来源、保留区、页对齐和简化限制；未在本工程实现的 E820/UEFI 仅列为可行方法，不写成已经执行。

### 4.4 功能模块二任务一：First Fit 理解与思考

**负责人：2410933 马禹翔**

#### 4.4.1 任务规格与分析方法

First Fit 维护按块头地址递增的空闲链表。申请 `n` 页时从表头开始寻找第一个 `property >= n` 的块；释放后把新区间插回地址顺序，并与物理相邻的前后块合并。分析重点不是只复述循环，而是跟踪每一步的块头标志、`property`、链表位置和 `nr_free` 是否一致。

前置条件是调用者传入正页数；`init_memmap()` 的区间已经由 `page_init()` 判定为可用、完整且尚未交给分配器的页面。后置条件是链表中每个节点代表一个不重叠的连续空闲块，所有块的长度总和等于 `nr_free`。

#### 4.4.2 四个核心函数

**`default_init()`** 将哨兵头初始化为自环，并把 `nr_free` 清零。此时只建立算法内部空状态，还没有真实可分配页。

**`default_init_memmap(base,n)`** 不是探测占用页。上层已经确认该区间可用，函数中的 `assert(PageReserved(p))` 检查这些描述符仍处于“尚未交给分配器”的统一保留状态。循环清除旧标志、旧长度和引用计数；随后只在 `base` 上设置 `property=n` 和 `PG_property`，将整个区间作为一个块插入地址有序链表，最后令 `nr_free += n`。

**`default_alloc_pages(n)`** 先用总量快速排除明显失败，再顺序遍历链表。找到第一个足够大的块后删除旧块头。如果块长度大于请求，剩余部分从 `page+n` 开始，成为新的块头并保留在原来的有序位置；成功后清除被分配块头的 `PG_property`，`nr_free` 精确减少 `n`。它选择的是第一个可用块，不保证剩余最小。

**`default_free_pages(base,n)`** 逐页断言页面不是 Reserved、也不是现有空闲块头，然后清理状态，以 `base` 建立新块头并令 `nr_free += n`。插入地址有序链表后，只需检查前驱和后继：若 `prev + prev->property == base` 就向左合并；再从合并后的块头检查右侧，若 `base + base->property == next` 就向右合并。地址相邻是 First Fit 合并的充分条件之一，而 Buddy 还要求同阶且真正互为伙伴。

#### 4.4.3 改进空间与代价

设空闲块数为 `B`，当前 First Fit 的分配最坏需要扫描 `O(B)`；释放还需要寻找插入点。可以考虑：

1. **游标式 Next Fit**：从上次停止位置继续扫描，可能改善反复从头遍历的开销，但结果依赖历史，可能错过低地址更合适的块。
2. **按大小建立平衡树或尺寸桶**：能更快定位可容纳请求的块，但释放、拆分、合并时必须同时维护地址关系与大小索引，元数据和一致性成本更高。
3. **延迟合并或定期整理**：可降低每次释放的即时成本，但在整理前更容易因外部碎片导致大块申请失败。
4. **改用 Best Fit/Buddy**：Best Fit 尝试减少当次剩余，Buddy 使拆分合并更规则；前者仍可能留下很多小洞，后者对非 2 次幂请求产生内部碎片。

因此不存在对所有负载都绝对更好的策略。优化结论需要结合请求分布、碎片率和时间开销测量，不能只凭复杂数据结构断言一定更快。

**分析提示词：** [MYX-P3：初始化登记不等于内存探测](prompt.md#myx-p3)、[MYX-P4：空闲块插入顺序](prompt.md#myx-p4)。约束只读分析、不修改原有实现；结果需同时解释链表顺序、块头标记和总空闲页数。

### 4.5 功能模块二任务二：Best Fit 实现与接入

**负责人：2410673 韩羽宸**

**算法目标和状态约定。** 对 n 页申请，Best Fit 选择所有能满足申请的连续块中最小者；相同大小选低地址块。假设按地址有 12、6、9 页三个空闲块，请求 5 页：First Fit 会选择第一个 12 页块，本实现选择 6 页块，交付前 5 页、留下 1 页。Best Fit 的“最优”只针对当前剩余块大小，不能保证未来整体最优。

链表仍按地址排序，选择时才比较大小。地址顺序服务于释放合并，Best Fit 不要求链表必须按大小排序。内部 `static free_area_t free_area` 保存哨兵 `free_list` 和总空闲页数 `nr_free`；每个连续空闲块只有块头入链，块头的 `PG_property` 有效，`property` 是该块页数，不是空闲块个数。非块头不保留块头标志，分配后的旧长度要清零。

`Page.ref`、`flags`、`property`、`page_link` 分别表示引用、状态、块头长度和链表节点。`le2page(le,page_link)` 利用 `to_struct` 从成员地址减去字段偏移，返回所属 `Page`；不是从链表节点数值推导物理地址。描述符按物理页顺序排列，所以比较同一数组内的指针和 `base+n` 可以表达物理连续关系。标志位宏在当前工程直接修改字段，不能因为手册旧注释提到原子操作就宣称本算法已经支持并发。

**SPEC 与最终提示词。** [HYC-P2](prompt.md#hyc-p2) 规定：正页数前提；选择最小足够块，同尺寸取低地址；成功精确交付 n 页；尾部拆分；释放时仅按物理邻接合并；无合适连续块时返回 NULL 且状态不变。已有 `basic_check()`、`best_fit_check()` 和注册接口保持不变，不能为通过而修改评分。

**各核心接口如何协同。**

- `best_fit_init()`：把循环链表设为空，计数归零，尚不登记任何物理页。
- `best_fit_init_memmap(base,n)`：要求正页数、有效描述符范围、输入仍保留；初始化这些页，设置新块头，通过内部插入合并登记，总数只增加 n。多个区间乱序登记也能按地址组织。
- `best_fit_alloc_pages(n)`：断言 n>0；总量不足立即失败。扫描所有足够大的块，只有候选更小时才替换，所以相同大小保留先遇到的低地址块；精确匹配可提前退出。无候选返回 NULL，既不拆块也不改计数。
- 选择成功后，删除原块头、清除旧标志和长度；有剩余时以 `best+n` 为尾块头，把它插回原链表位置，保持地址顺序；计数只减少 n。精确匹配不生成零长度尾块。
- `best_fit_free_pages(base,n)`：调用者提供有效已分配区间；逐页清理状态，设置新块头，插入并尝试左右合并，总数只增加本次归还的 n。不是通过观察某个页的 ref 为零就能证明任意释放合法。
- `best_fit_insert_block(base)`：找到地址插入点，断言不与左右块重叠；先并左，令左块成为头，再从合并结果检查右邻居，故能一次连接两边。旧头标志与长度被清除、节点自环。链表相邻还不够，必须满足 `left+left->property==base` 等物理邻接条件。
- `best_fit_nr_free_pages()` 返回总空闲页数；注册结构将以上五个回调及原有 `best_fit_check()` 交给框架，`init_pmm_manager()` 选择 `&best_fit_pmm_manager`。只完成算法但没有切换管理器时，原内核运行的仍可能是 First Fit。

原有测试会暂时置空链表而尚未同步改计数，所以实现不能假定 `nr_free>=n` 必然存在候选。搜索无结果仍返回 NULL，兼容原测试的状态约定。原有 `basic_check()`、`best_fit_check()` 保持不变，并未另写“更容易通过”的版本替代它们。

**实现迭代与限制。** 本人完整模块、管理器注册和切换均已落到 [best_fit_pmm.c](../code/kern/mm/best_fit_pmm.c) 与 `pmm.c`，标记 `2410673`。原有检查 6/6、两项任务 PASS、评分 20/20 和补充模型核对均通过。未观察到需要改测试或修正选择算法才能通过的情况；实际集成中遇到的启动取指故障已在 4.1 分析。

零页申请违反接口前提并触发断言；本实现不维护完整分配历史表，不能声称检测任意重复释放、跨申请错误释放和所有非法指针。当前是单核启动阶段顺序调用的实验，没有并发锁。

**思考题：Best Fit 是否还有改进空间？** 设空闲块数为 B，当前分配最坏扫描 O(B)，精确匹配可提前停止；释放需处理 n 个描述符并定位插入点，约为 O(n+B)。可增加按大小的平衡树等索引快速找最小合适块，同时保留按地址定位邻居的能力；代价是拆分、合并和删除都要同步索引，增加元数据和一致性维护。尺寸分组也可减少搜索，但分组过粗可能改变严格 Best Fit 语义。

此外，最小剩余策略可能留下大量小块。立即合并只能合并已经空闲且物理相邻的区间，不能跨越已分配页；两个 3 页块不能满足一个 4 页连续请求，尽管空闲总量足够。这是外部碎片。按页分配小对象留下页内空间则涉及另一层内部碎片，需联系队友的 SLUB。本人没有实现上述索引或做速度基准，报告不给出未经测量的加速结论。

### 4.6 功能模块二任务三：Buddy System

**负责人：2410933 马禹翔**

#### 4.6.1 功能规格与接口约定

Buddy 把空闲页分成大小为 `2^order` 的块，每个 order 有一条独立链表。公共头文件只导出：

```c
extern const struct pmm_manager buddy_pmm_manager;
```

初始化、登记、分配、释放、计数和辅助函数均为 `buddy_pmm.c` 内部 `static` 实现。非 2 次幂请求向上取整，例如 3 页实际占用 4 页，5 页实际占用 8 页；分配计数和释放校验都使用这个实际块大小，避免申请和归还语义不一致。

关键不变量如下：

- 空闲块头设置 `PG_property`，`property` 为该阶实际页数，并且只出现在对应 order 链表中一次。
- 空闲块内部页不设置 `PG_property`，不独立进入链表。
- 已分配块头不设置 `PG_property`，但保留实际块大小用于释放校验。
- `buddy_nr_free` 是所有阶空闲页之和；拆分和合并不改变它，只有真正分配和释放改变它。
- order 为 `k` 的块必须按 `2^k` 物理页号对齐。伙伴页号为 `base_ppn ^ (1 << k)`。
- 只有范围内、同阶、空闲且真正互为伙伴的块才能合并；地址相邻但不满足 XOR 关系的块不能合并。

#### 4.6.2 核心实现

`buddy_init()` 初始化 0～31 阶链表和每阶块计数，并清零总空闲页数。

`buddy_init_memmap(base,n)` 先清理已确认可用的描述符，再从低地址开始，反复选择“不超过剩余长度且当前物理页号满足对齐”的最大 2 的幂块。这样即使起点和长度不是 2 的幂，也不会生成越界或错误对齐的块。每个分块通过统一的合并插入函数登记，总计数最后只增加原始 `n`。

`buddy_alloc_pages(n)` 计算最小目标阶，从该阶向上寻找第一个非空链表。取出高阶块后逐级二分：左半继续拆分，右半进入低一阶空闲链表，直到目标阶。最后总计数减少实际块大小，并在返回块头保存该大小。

`buddy_free_pages(base,n)` 用相同规则重新计算阶，校验范围、对齐、块头状态和实际大小，清理整块描述符，总计数只增加一次。随后计算伙伴：伙伴同阶且空闲时先从链表删除，选择低地址作为合并后的块头并提高一阶，循环直到不能继续，最后把结果插入对应链表。

最终注册对象把上述回调交给通用框架。普通构建仍选择 Best Fit；Makefile 新增默认关闭的测试配置：

```bash

make BUDDY=1 qemu
```

`CONFIG_BUDDY_PMM` 只在显式设置 `BUDDY=1` 时定义，因此原始评分和最终默认管理器不受影响。

#### 4.7.2 两层接口和地址转换

```text
kmalloc(bytes) / kfree(ptr)
  -> SLUB：分类、空闲槽链、bitmap、在用计数、活动块登记
  -> alloc_pages(n) / free_pages(base, n)
  -> 默认 Best Fit 的空闲物理页管理
```

`alloc_pages()` 返回 `struct Page *`，不能直接当作页面数据地址。本实现将转换集中在 `slub_page_kva()`：先检查描述符是否属于 `pages` 数组、对齐及页数是否有效，再调用 `page2pa(page)`，按 `KVA = PA + va_pa_offset` 转换，并检查溢出与映射范围。

当前 `KADDR` 被注释，因此没有直接调用不可用宏，也没有把虚实地址加减散落到每个分配、释放函数。对象层向下仍使用原有页接口，不改变 Best Fit 的实现或测试。

#### 4.7.3 页面布局与对象元数据

公共 `slub_block` 保存 magic、块类型、原始 `Page *`、申请页数和活动链表节点。`slub_slab` 再保存分类号、容量、`inuse`、空闲槽链头、分类链节点和分配 bitmap；`slub_large` 保存大对象请求大小等信息。

```text
小对象：| 对齐后的页内管理头 | 槽0 | 槽1 | ... | 槽N-1 | 尾部余量 |
大对象：| 管理头及对齐填充   | 调用者的 size 字节       | 末页余量 |
```

空闲槽位开头保存下一个空闲对象的指针；分配后这段空间完全交给调用者，不额外为每个在用对象插入独立头。分配状态在 slab 头的 bitmap 中记录，数量由 `inuse` 记录，因而同时支持复用、统计和重复释放检查。

本次 RV64 的小对象头对齐后为 128 字节，容量为 `floor((4096 - 128) / class_size)`：

| size class | 16  | 32  | 64  | 128 | 256 | 512 | 1024 | 2048 |
| ---------- | --- | --- | --- | --- | --- | --- | ---- | ---- |
| 每页容量       | 248 | 124 | 62  | 31  | 15  | 7   | 3    | 1    |

这些值来自当前结构布局，不是所有 SLUB 的通用规定。各分类的 `partial_slabs[]` 只登记仍有空闲槽的非空 slab；所有存活块另外登记在 `active_blocks` 中。

#### 4.7.4 核心函数与状态变化

**小对象分配。** `kmalloc()` 扫描八档分类后调用 `slub_alloc_small()`。若没有可分配 slab，`slub_new_slab()` 用 `alloc_pages(1)` 取页，计算容量并建立空闲槽链。分配时弹出一个槽、设置 bitmap、增加 `inuse`；满页从 partial 链移除。同类后续请求可以复用槽位，不必每个对象都调用页分配器。

**大对象分配。** `slub_alloc_large()` 先检查头部加法溢出，再计算：

```c
total = size + LARGE_HEADER_SIZE;
npages = total / PGSIZE + (total % PGSIZE != 0);
```

这种写法避免 `total + PGSIZE - 1` 的再次溢出。本次大对象头与对齐共占 64 字节，因此 4096 字节请求实际需要两页，8192 字节请求需要三页。空闲页总数足够也不能保证连续块申请成功，仍须处理 `alloc_pages()` 返回 NULL。

**释放前校验。** `kfree()` 先处理 NULL，再检查范围与对齐，用 `slub_find_block()` 在可信活动头链表中寻找归属。没有直接把任意输入向下取整后解引用为管理头，避免读取不可信元数据。

**小对象释放。** `slub_slot_index()` 校验有效槽起点，bitmap 判断是否仍在用。确认后清位、减少 `inuse`。原来满页释放一个对象后重新加入 partial 链；仍非空时把槽压回空闲链；最后一个对象释放后，移除链节点并归还整页，不保留空 slab。

**大对象释放。** 输入必须是管理头之后的准确返回地址，内部指针不能释放整块。`slub_release_block()` 先保存原始页描述符和页数，注销活动块并使 magic 失效，再调用 `free_pages(page, npages)`；归还后不再读页内头。

**统计。** `slub_get_stats()` 遍历活动块，分别统计存活对象、小对象 slab 页、大对象页。释放查找与统计存在遍历开销，本实现以清晰可验证为主，不声称具有 Linux SLUB 的生产性能。

#### 4.8.1 双 GDB 与 QEMU 页表翻译

**双 GDB 与三个终端。** 宿主 GDB 看到的是 QEMU 的 C 源码、宿主线程和模拟状态；客体 GDB 看到的是 RISC-V 指令、内核符号和寄存器。前者加载 QEMU，后者加载 `bin/kernel`，不是把同一个目标打开两次。

```mermaid
flowchart LR
    H[终端2 宿主GDB] -->|启动并调试| Q[QEMU进程]
    G[终端3 RISC-V GDB] -->|gdbstub| Q
    Q --> V[模拟CPU与ucore]
    Q -->|真实串口文件| T[终端1 日志查看]
```

QEMU 的 `-S` 暂停模拟 CPU，`-gdb tcp:127.0.0.1:1234` 开启客体连接；QEMU 进程仍可处理调试请求。宿主断点则暂停 QEMU 本身，此时客体命令等待，需要先继续宿主。区分这两种暂停，才能理解为什么终端 3 看似“没有反应”。相关选项职责见 [QEMU 官方 gdbstub 文档](https://www.qemu.org/docs/master/system/gdb.html)。

宿主设置 `handle SIGPIPE nostop noprint pass`，实际显示 Stop=No、Print=No、Pass=Yes，保留信号传递而不因此暂停。SIGPIPE 通常与向已关闭连接写入有关；本轮未故意复现省略配置后的现象，不写成已观察到的 bug。断点按内核代码页和 `MMU_INST_FETCH` 限定，减少固件访问引起的无关停止。

![宿主GDB命中QEMU取指翻译入口](images/hyc/06_宿主GDB命中QEMU源码断点.png)

图06是本人现场在宿主端取得的原图。实际请求地址为 `0xffffffffc0200046`，访问类型为取指；调用栈和 `cpu_helper.c:1184` 清晰可见。栈中宿主指针和宿主代码地址属于 QEMU 进程，不能当作模拟机器物理地址。此处只是进入翻译慢路径，还不是完成查表。

宿主继续后，客体在当前 ELF 的 `kern_init` 第一条指令停住。使用 `hbreak *0xffffffffc02000ee` 指定实际入口，避免仅按源码行设置断点时受函数序言影响。

![客体GDB进入内核C入口](images/hyc/07_客体GDB进入内核C入口.png)

图07的 PC 为 `0xffffffffc02000ee`，SP 为 `0xffffffffc0205000`，satp 为 `0x8000000000080205`。按配置的读取顺序，`$1=0` 是 root[2]，`$2=0x200000cf` 是 root[511]，说明过渡映射已经撤销。寄存器旁的负十进制数是相同位模式的有符号显示，应按十六进制解释 satp 字段。

**观测目标与选择理由。** 本次使用 QEMU 7.0.0，宿主 GDB 调试 QEMU 实现，RISC-V GDB 控制 ucore。选择内核从低地址跳到高地址标签时发生的一次取指，实际虚拟地址为 `0xffffffffc0200046`，访问类型为 `MMU_INST_FETCH`。该位置在现有 `entry.S` 中必然执行，与上述环境验证的观测目标一致，不需要临时向正式代码插入访存或修改页表。

这个地址位于 `kern_init` 所在页，但不是 C 入口 `0xffffffffc02000ee`。按代码页设置条件，可以捕获更早的首次高地址取指，避免该页已经缓存后再期待 C 入口精确地址触发同样的翻译。它是内核指令读取，不是用户程序的数据读写。页表翻译函数还会被调试器读取客体内存时调用，因此断点额外限制 `is_debug=false`，确认捕获的确是 CPU 执行产生的访问。

**源码调用路径和入口分支。** 双 GDB 实测的外层取指路径为 `tb_htable_lookup -> get_page_addr_code -> get_page_addr_code_hostp -> tlb_fill -> riscv_cpu_tlb_fill`。本轮继续观察到 `riscv_cpu_tlb_fill` 在 `target/riscv/cpu_helper.c:1278` 通过单阶段分支调用 `get_physical_address`，宿主调用栈直接显示了这次调用。上述路径属于本次取指翻译慢路径，不能直接替代所有数据访存或 TLB 命中路径。

条件断点按当前 ELF 推导的内核代码页设置：

```gdb

```

实际参数为 `first_stage=true`、`two_stage=false`、`is_debug=false`，客体特权级为 1，即 S 态。这里的一阶段/两阶段指虚拟化翻译，与 Sv39 的三级页表不是同一个概念。本次没有进入虚拟化第二阶段，也没有走 M 态或 Bare 的直接返回分支，而是从 `env->satp` 取得普通 S 态的页表配置。

**从 satp 找到页表。** 实测 `satp=0x8000000000080205`。MODE 为 8，对应 Sv39；ASID 为 0；根表物理页号为 `0x80205`。因此根表物理地址为 `0x80205 << 12 = 0x80205000`。这里保存的是物理页号，不是高地址符号 `0xffffffffc0205000`，也不是 QEMU 宿主进程中的对象指针。

`get_physical_address` 的 821～842 行先提取 `base` 和 `vm`，再由模式选择 `levels=3`、`ptidxbits=9`、`ptesize=8`。这说明 Sv39 最多用三个 9 位索引查表，每项 8 字节。随后代码检查虚拟地址高位是否合法，避免将不符合符号扩展要求的地址直接用于遍历；本次高地址通过该检查。Sv39 的三级结构以及各级允许叶项、大页须满足对齐的体系结构依据见 [RISC-V 官方 Supervisor 规范](https://docs.riscv.org/reference/isa/priv/supervisor.html)。

**循环、索引和 PTE 读取。** 本版本的主要遍历循环位于 876 行，`i` 从 0 开始，表示从根向下的第几轮；它与一些教材从顶层编号 2 再递减的写法不同。`ptshift=(levels-1)*ptidxbits` 初值为 18；每向下一层减 9。索引提取还要加上 12 位的普通页内偏移，因此根层取的是虚拟地址的第 38～30 位。

```text

VPN[2]       = 511
VPN[1]       = 1
VPN[0]       = 0
4 KiB offset = 0x46
i            = 0
ptshift      = 18
base         = 0x80205000

```

```text
vpn = VA >> 12
PA  = ((ppn | (vpn & ((1 << ptshift) - 1))) << 12)

```

1 GiB page base = 0x80000 << 12 = 0x80000000
1 GiB offset    = VA & 0x3fffffff = 0x200046
PA              = 0x80000000 + 0x200046 = 0x80200046

#### 4.8.2 TLB 查询、未命中、填充与命中

**负责人：2410933 马禹翔**

##### TLB 为什么有效

没有 TLB 时，每次访存除访问最终数据外，还可能需要逐级读取页表。TLB 缓存近期虚拟页到物理页及权限的翻译，命中后避免重复页表遍历。程序通常具有时间局部性（短时间重复访问相同代码或数据）和空间局部性（相邻地址往往落在同一页或附近页），所以少量翻译项即可覆盖大量访存。

TLB 不是普通数据缓存：它保存地址翻译和权限。修改页表后需要用 `sfence.vma` 建立页表更新与后续翻译之间的正确关系；这不等价于刷新普通数据缓存或指令缓存。

##### QEMU 4.1.1 中的查询、未命中与填充

本机源码位于 `/home/s1nk/qemu-4.1.1`，带调试信息的程序是 `riscv64-softmmu/qemu-system-riscv64`。它与手册版本一致。关键路径如下：

```text
取指或数据访问
  -> 计算 mmu_idx 和 tlb_index
  -> tlb_entry 取得直接映射项
  -> tlb_hit 比较虚拟页号
       命中：使用 entry->addend 形成宿主地址，直接继续访问
       未命中：检查 victim_tlb_hit
           victim 命中：交换回主 TLB
           仍未命中：tlb_fill
               -> riscv_cpu_tlb_fill
               -> get_physical_address 遍历 RISC-V 页表
               -> PMP/权限检查
               -> tlb_set_page
               -> tlb_set_page_with_attrs 写入主 TLB
```

对应源码位置：

- `include/exec/cpu-all.h:348-361`：`tlb_hit_page()` 和 `tlb_hit()`，比较页对齐后的虚拟地址与条目地址。
- `include/exec/cpu_ldst.h:163-181`：`tlb_index()` 与 `tlb_entry()`，根据虚拟页和 MMU 索引选择直接映射槽位。
- `accel/tcg/cputlb.c:1023-1037`：取指路径 `get_page_addr_code()`；主 TLB 不命中时先查 victim TLB，再调用 `tlb_fill()`。
- `accel/tcg/cputlb.c:1252-1280`：数据读取慢路径使用同样的主表、victim 表和 fill 次序。
- `target/riscv/cpu_helper.c:435-474`：`riscv_cpu_tlb_fill()` 调用 `get_physical_address()`，翻译和 PMP 检查成功后调用 `tlb_set_page()`。
- `accel/tcg/cputlb.c:697-838`：`tlb_set_page_with_attrs()` 计算索引，必要时把旧项放入 victim TLB，并写入 `addr_read/addr_code/addr_write`、`addend` 和 IOTLB 数据。

QEMU 的软件 TLB 是模拟器为了加速客体访存而维护的数据结构，不等于真实处理器厂商的硬件阵列实现。但它模拟了软件可见的关键逻辑：按地址空间和虚拟页查翻译、区分权限、未命中时查页表、页表或模式变化后失效。

##### 调试策略与证据边界

只在 `riscv_cpu_tlb_fill()` 断点能证明发生了未命中慢路径，但不能单独证明命中；命中恰恰会绕过该函数。因此现场应取得两类证据：

1. **未命中与填充**：在 `riscv_cpu_tlb_fill`、`tlb_set_page_with_attrs` 设置断点，记录同一虚拟页的 `address/vaddr/paddr/prot/mmu_idx`，证明查页表后写入条目。
2. **随后命中**：在 `get_page_addr_code` 的 `tlb_hit` 判断附近停住，记录 `addr`、`entry->addr_code` 和 `tlb_hit(...)` 返回真，并确认这次没有再次进入 `riscv_cpu_tlb_fill`。

为了避免固件阶段大量无关事件，实际会话先由客体 GDB 启动模拟 CPU，再由宿主 GDB 对 `0xffffffffc0200000` 内核代码页设置条件断点。宿主 GDB 调试的是 x86-64 QEMU 进程，客体 `gdb-multiarch` 调试的是 RISC-V ucore；宿主暂停时客体会等待，不能把等待误判成死机。实际截图表明第一次访问时 `entry->addr_code=0xffffffffffffffff`，随后进入 `riscv_cpu_tlb_fill()` 和 `tlb_set_page_with_attrs()`；填充后再次访问同一页时，`entry->addr_code=0xffffffffc0200000`，与 `addr=0xffffffffc0200046` 的页基址相同。GDB 无法直接调用被优化内联的 `tlb_hit()`，因此结合源码定义和页基址相等关系判断命中，而不把 `No symbol "tlb_hit"` 误认为 QEMU 运行失败。

##### 调试目标与关键模块

客体侧用 `hbreak`、`info registers`、`x/i $pc`、`stepi` 确认真实 RISC-V 指令；宿主侧直接启动带符号 QEMU，在已知必经地址设置条件断点。两次观察使用配对的默认内核 ELF/镜像，但客体侧为 QEMU 11.1.1，源码侧为 4.1.1。

| --------------------------- | ------------------------------------------- |
| `riscv_cpu_tlb_fill()`      | 调用翻译，结合访问类型、权限处理成功或异常，并建立软件映射               |
| `get_physical_address()`    | 按特权级与分页模式决定是否查表；Sv39 下读取解释 PTE，不是对所有地址减固定偏移 |

| `tlb_set_page_with_attrs()` | 把映射、属性和供宿主访问 RAM 的加数写入软缓存                   |

对应 [QEMU 4.1.1 cpu_helper.c](https://github.com/qemu/qemu/blob/v4.1.1/target/riscv/cpu_helper.c) 与 [cputlb.c](https://github.com/qemu/qemu/blob/v4.1.1/accel/tcg/cputlb.c)，实际停点见 5.5。

##### Bare/Sv39 与真实硬件的比较

两次宿主观察都在 S-mode。Bare 访问 `0x80207000` 时 `satp=0`，直接同值返回，不读页表；Sv39 访问 `0xffffffffc0207018` 时 MODE=8，读取根项并解释叶映射。两者成功后都进入软件 TLB 填充。

| 对比项  | 真实 RISC-V 架构层面             | 本次 QEMU 软件实现                                |
| ---- | -------------------------- | ------------------------------------------- |
| 缓存目的 | 缓存翻译及权限，减少重复查表             | 除减少翻译，还服务于快速访问宿主内存                          |
| Bare | 不执行 S/U 页表翻译，但不等于绕过全部物理保护  | 不遍历页表，仍可能缓存物理内存访问结果                         |
| 缓存内容 | 页映射、权限与地址空间标识；微结构由具体实现决定   | 可见 `addr_read`、`addr_write`、`addend` 等 C 字段 |
| 地址终点 | 架构物理地址                     | 客体物理地址还需定位到宿主 RAM 或设备区域                     |
| 大页   | 架构允许不同大小叶映射，具体 TLB 组织未在此测量 | 此版本此路径按 4096 字节填充条目，即使叶项是 1 GiB             |

最直接的证据是图 08 与 10：高低两种客体页地址对应同一物理页，`addend` 不同，`VA page + addend` 却得到同一宿主 RAM 页指针。这是模拟器的宿主定位过程，不能把这些 C 字段直接当作真实硬件 TLB 字段。

##### 调试中的真实问题与收获

1. **宿主与客体架构不同。** ARM 主机上的 x86 Linux 容器曾使宿主 GDB 报 `Couldn't get registers: Input/output error`。改用原生 Linux ARM64 容器，先验证 GDB 能调试自己启动的进程，再调试 QEMU。RISC-V 是被模拟架构，宿主调试器应匹配真正运行 QEMU 的环境。
2. **固件默认行为随版本不同。** QEMU 4.1.1 首次提示未指定 `-bios`、没有加载固件；显式增加 `-bios default` 后进入目标路径，不能套用另一版本默认行为。
3. **断点未命中不等于指令没执行。** 原计划观察读取 `boot_hartid`，但 `kern_init()` 先 `memset(edata, ...)`，已访问并缓存同一页。最终改为首次 BSS 写入 `0xffffffffc0207018`，稳定进入慢路径。这让我理解“访存执行过”与“翻译函数被调用”不是一回事。
4. **三级模式不等于读三张表。** 根项已是大页叶项，`levels=3、i=0、ptshift=18` 表示从最高级开始检查，不是走完三次循环。
5. **调试读不同于客体 load。** `x/gx` 是辅助检查，不能冒充客体 CPU 普通访存。本次证据结合真实 `sd/ld` 单步与宿主条件断点。

**学习与调试提示词：** [LZY-P5](prompt.md#lzy-p5)。要求区分版本、客体与宿主架构、实际访存与调试读、三级能力与实际叶项深度。

### 5.2 物理初始化与 Best Fit 验证

**初始化边界。** 隔离 RV64 测试内核直接包含正式 `pmm.c`，使用真实结构和宏；默认场景读取真实 DTB，其余场景由测试驱动替换两个 getter 的返回值，不改正式 DTB 模块。13 个场景全部通过：

#### 5.5.3 Bare/Sv39 的六步对比

**负责人：2410936 林子媛**

##### 5.5.3.1 第一步：客体分页前的真实 store

QEMU 用 `-S -gdb tcp:127.0.0.1:1235` 启动，RISC-V GDB 加载配对内核 ELF，而不是没有源码符号的裸镜像。本次在 `0x80200014` 设断点并单步执行 `sd a1,0(t0)`。

![客体 GDB 分页前 Bare 访存](images/lzy/05_客体GDB分页前Bare访存.jpeg)

图 05 中 `priv=1` 为 S-mode，`satp=0`，目的地址 `t0=0x80207008`，数据 `a1=0x87e00000`。执行后 PC 到 `0x80200018`，目的位置保存了 DTB 地址，证明真实 store 已执行。

物理 PC 显示 `??` 不代表失败：符号按高虚拟地址链接，此时尚未跳到高地址。`Hardware assisted breakpoint` 是 QEMU 为客体调试提供的断点类型，不代表用了真实 RISC-V 硬件。

##### 5.5.3.2 第二步：客体分页后的真实 load

继续到 `dtb_init+0x2e`，本次为 `0xffffffffc0200270`，执行 `ld a1,0(s0)`：

![客体 GDB 分页后 Sv39 访存](images/lzy/06_客体GDB分页后Sv39访存.jpeg)

图 06 中 `satp=0x8000000000080206`，MODE=8、ASID=0、根表物理基址 `0x80206000`。`s0=0xffffffffc0207008`，根索引 511，PTE 为 `0x200000cf`。根级叶项给出物理基址 `0x80000000`，低 30 位偏移是 `0x207008`，故物理地址为 `0x80207008`。load 后 `a1` 得到先前保存的 `0x87e00000`。

这联系了低地址写入与高地址读回，但图中 PTE 解码仍是调试辅助计算；QEMU 真正执行读表的证据在后续宿主截图。

##### 5.5.3.3 第三步：宿主观察 Bare 分支

宿主 GDB 加载调试版 QEMU，显式指定 `-bios default` 和内核镜像，设置条件：

```gdb
break get_physical_address if addr == 0x80207000 && mmu_idx == 1 && access_type == 1
run
```

![宿主 GDB 观察 QEMU Bare 路径](images/lzy/07_宿主GDB观察QEMU的Bare地址路径.jpeg)

图 07 中 `satp=0、priv=1、access_type=1`，是 S-mode Bare store。实际进入 `VM_1_10_MBARE` 分支，得到 `VA=PA=0x80207000、prot=7`。`prot` 是 QEMU 页访问权限组合，不是全部物理安全授权，之后仍有 PMP 等检查。

调用栈包含 `get_physical_address -> riscv_cpu_tlb_fill -> tlb_fill`。因此结论是“不走 S/U 页表遍历”，不是“模拟器完全跳过所有辅助访存路径”。

##### 5.5.3.4 第四步：确认 Bare 仍填充软 TLB

翻译函数返回后继续到 `tlb_set_page_with_attrs()`，观察条目写入完成的状态：

![Bare 模式仍填充 QEMU 软件 TLB](images/lzy/08_Bare模式仍填充QEMU软件TLB.jpeg)

图 08 中 `mmu_idx=1、prot=7、size=4096`，虚拟页与客体物理页都是 `0x80207000`。条目还有 `addend=0xffff0be00000`，客体页地址加上它得到宿主 RAM 页指针 `0xffff8c007000`。

即使没有启用页表翻译，模拟器仍要高效找到宿主进程中承载 RAM 的位置。不能由软件 TLB 的存在推断 Bare 下硬件仍在查 Sv39 页表。

##### 5.5.3.5 第五步：读取 Sv39 根项并形成物理地址

为避开同页已被缓存的后续读，选择首次 BSS 写入：

```gdb
break get_physical_address if addr == 0xffffffffc0207018 && mmu_idx == 1 && access_type == 1
```

![宿主 GDB 观察 Sv39 根页表读取](images/lzy/09_宿主GDB观察Sv39根页表读取.png)

按图 09 可逐步核对：

1. `satp=0x8000000000080206`，根表物理地址为 `0x80206000`。
2. `VA=0xffffffffc0207018`，`VPN[2]=511`。
3. 一项 8 字节，所以 PTE 地址为 `0x80206000 + 511*8 = 0x80206ff8`。
4. RV64 分支用 `ldq_phys()` 读得 `0x200000cf`，是有效大页叶项，不继续查下一级。
5. `levels=3、i=0、ptshift=18` 表示从根级开始。根级物理基址结合低 30 位偏移形成 `0x80207018`。

QEMU 4.1.1 该函数返回的是基本页对齐的物理基址 `0x80207000`，完整字节地址还需加本次偏移 `0x18`，不能混淆页基址与实际访存地址。

##### 5.5.3.6 第六步：比较两种模式的软件缓存结果

![Sv39 地址形成与软件 TLB 对比](images/lzy/10_Sv39地址形成与QEMU软件TLB对比.jpeg)

图 10 中请求 `0xffffffffc0207018` 对应 `0x80207018`，缓存的页映射为 `0xffffffffc0207000 -> 0x80207000`，大小 4096。其 `addend=0xffffcbe00000`，相加仍得到 `0xffff8c007000`，与图 08 相同。

两图来自同一宿主运行：客体地址和加数不同，但定位到同一宿主 RAM 页。根级 1 GiB 叶映射与此版本按 4 KiB 建立缓存条目不矛盾，两者处于不同实现层面。宿主 ASLR 保持开启，重启后宿主指针可以变化，不能把该绝对值写入算法。

最后用全新 QEMU 进程再次复现，核对 Bare 同值翻译、Sv39 store 结果、根叶项、软 TLB 页与权限、两种模式的宿主页一致性，5 项检查全部通过。关键输入和结果已写入正文，不依赖额外调试说明文档作为论证。

### 6.2 重要但本实验未覆盖的 OS 知识

三人的总结合并如下，不把理论理解写成已实现功能：

1. **进程独立地址空间与用户隔离。** 尚无完整进程页表创建、切换和销毁，当前内核大页并非用户内存管理。
2. **缺页异常、按需分页和页面置换。** 尚无磁盘后备存储、工作集、Clock/LRU 或换入换出；有 A/D 位不等于实现了这些策略。
3. **写时复制、共享内存和文件映射。** 缺少进程、文件系统及引用计数驱动的映射生命周期。
4. **多核和中断并发。** 尚无分配器锁、per-CPU slab、远程释放和完整内存序保证，不能将顺序测试通过外推为 SMP 安全。
5. **跨核 TLB shootdown 与 ASID 管理。** 当前单 HART、ASID=0，没有跨 CPU 失效、ASID 回收复用验证。
6. **通用物理内存拓扑。** 多段 RAM、保留区洞、NUMA、热插拔、迁移、压缩和设备内存尚未完整处理。
7. **生产级对象缓存和内存错误检测。** 尚无压力回收、保留阈值、构造析构、完整分配历史；当前保护不覆盖全部越界、错误指针或地址复用后的悬空引用。
8. **调度、进程同步与文件系统。** 它们会依赖动态内存，但不在本次页和对象分配的实现范围。

**用真实上下文定位问题。** 工具链错误提供命令与报错，Buddy 冲突提供选定管理器与保护信息，OpenSBI 后无内核输出则核对下一跳与入口。不能只说“运行失败”，更不能修改已有检查来掩盖不一致。

**让测试观察数据与资源。** 地址不同不代表有效载荷不重叠，对象数归零不代表页已归还，看到 panic 不代表命中目标分支。因此同时检查数据模式、各层统计和精确失败信息。

**用调试修正解释。** 我曾把三级页表理解成必走三层，把 Bare 理解成不用任何 TLB。根级叶项和 Bare 软件缓存的观察纠正了这些认识。AI 用于形成假设和设计操作，结论仍接受指令、寄存器、PTE、调用栈和测试检验。

报告因此保留“未发现新算法 bug”“未做实机 TLB 测量”“不识别全部悬空指针”等边界，不把未执行内容写成成功结果。

**实际问题汇总。**

| 问题                | 证据或原因                                   | 修正与验证                                   |
| ----------------- | --------------------------------------- | --------------------------------------- |
| 写 satp 后无法取指      | `scause=0xc`、`stval=0x80200038`，PC 仍低地址 | 增加临时恒等映射，进入高地址后删除；GDB 核对根项并运行检查         |
| 独立驱动缺少 SBI 退出定义   | 声明存在但链接无实现                              | 仅在独立驱动使用局部 SBI 退出，不改正式 SBI 模块           |
| GDB MI/参数与现场输入问题  | 异步控制未开启、字面引号或多行命令被误解析                   | 修正辅助脚本与输入顺序，重新执行真实单步                    |
| Buddy 自检隐含全局布局假设  | 测试依赖实际空闲块形状                             | 改为 16 页隔离 arena，保存恢复真实状态                |
| 增加测试输出后编译失败       | 缺少 `<stdio.h>`，被 `-Werror` 拒绝           | 补头文件后重新构建与运行                            |
| 工具链名称或宿主架构不匹配     | macOS 前缀不同；跨架构容器宿主 GDB 取寄存器失败           | 使用实际 `GCCPREFIX`；改原生 ARM64 调试容器并核验      |
| Buddy 与 SLUB 配置冲突 | 向上取整页数与本版精确页数契约不同                       | Buddy 独立配置跳过 SLUB，编译期禁止和 `SLUB_TEST` 同开 |
| 后续读不命中翻译断点        | 同页已被 BSS 清零访问并缓存                        | 选择首次 BSS store 观察 miss 路径，再比较 Bare/Sv39 |

没有观察到的新算法错误不补写成“AI 生成 bug”。生成前限制修改范围，是为了保留接口和已有检查的独立性；补测和独立模型则用于发现看似合理的代码中隐藏的状态错误，二者不能相互替代。
